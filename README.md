# 訪問看護　業務管理ステーション（日本訪問看護学会） - 引き継ぎメモ

## これは何か
日本訪問看護学会が所有する、訪問看護ステーションの「空き枠管理」「新規利用者の受け入れ提案」
「紹介元分析」を行う社内向けツール（アプリ名：訪問看護　業務管理ステーション）。管理者（スタッフ）
が共通のパスワードでログインし、全員で同じデータを見る・編集する形で使うことを想定している。
ログイン画面・ナビゲーション左上に学会ロゴと学会名を表示している（`index.php`の`.nav .brand`、
`login.php`の`.brand`。ロゴはPNGをBase64化して`<img src="data:image/png;base64,...">`として
直接埋め込んでいるため、追加のファイルアップロードは不要。ロゴを差し替える場合は新しい画像を
160×160px程度にリサイズしてBase64化し、両ファイルの該当箇所を置き換える）。

## 技術構成
- フロントエンド：Vanilla JS + HTML + CSS（`index.php`）。フレームワーク・ビルド工程なし。
- バックエンド：PHP + MySQL（CoreServerなどの一般的な共有レンタルサーバーで動く構成）。
- データはMySQLの `app_state` テーブルに1行（JSON文字列）として保存し、
  `api/state.php` 経由でフロントエンドと共有する（全管理者が同じデータを見る）。
- 認証は管理者共通の1つのパスワード（`config.php` にハッシュを保存、PHPセッションでログイン状態を管理）。
- デプロイ手順は `DEPLOY.md` を参照。

## データモデル（index.php内のJS、MySQLの app_state.data カラムにJSON文字列として保存）
```
state = {
  staff: [{name, role: '看護師'|'理学療法士'|'作業療法士'|'言語聴覚士'|'事務員', qualifications: string[]}, ...],
  // qualifications の例: ['特定行為看護師','皮膚・排泄ケア認定看護師'] など。複数可・自由記述の資格も可
  // role は「①②の空き状況画面・時間帯設定・空き枠数の計算調整のどれを共有するか」を決める単位ではなく、
  // 個々のスタッフの実際の職種（③新規登録・提案での訪問頻度パターン・希望曜日などが職種ごとに独立する単位）。
  // 理学療法士・作業療法士・言語聴覚士は roleGroup(role) がいずれも 'セラピスト' を返すため、
  // ②空き状況・slotLabels・staffBuffer・⑨設定の時間帯/勤務体系テーブルは3職種で共有する
  // （詳細は下の「職種（role）とロールグループ」の項を参照）。
  slotLabels: { '看護師': string[], 'セラピスト': string[] }, // 時間帯の名称。看護師／セラピスト（PT・OT・ST共有）で独立（並び替え可能）
  staffWorkSlots: { [staffName]: { [day]: number[] } }, // 曜日ごとに「その日のうち実際に勤務する時間帯（枠index）」の配列
  // 例：{ "山田花子": { "月": [0,1,2,3,4,5], "土": [0] } } → 月曜は全枠勤務、土曜は最初の枠だけ勤務
  staffBuffer: { '看護師': number, 'セラピスト': number }, // ①②の空き枠数計算・③の新規提案の候補選定の両方で差し引くスタッフ人数
  bookings: {
    [bookingId]: {
      staff, day, slotIdx,
      weeks: number[],                  // 1-5。[1,2,3,4,5]なら毎週、[1,3]なら隔週、[1,3,5]なら隔週(第1・3・5週)など
      patternValue,                     // 'weekly'|'daily'|'daily7'|'biweekly_13'|... （登録時の頻度パターン）
      name, disease, insuranceType, serviceDuration, alone, careManager, hospital, district, timeNote, note, startDate,
      pairId: string | null,
      hospitalized: boolean               // 入院中フラグ（デフォルトfalse相当。省略時はfalse扱い）
      // insuranceType: '医療保険'|'介護保険'|'精神'|'小児'（任意）。serviceDuration: '30'|'60'|'90'（分）
      // district: ⑨設定「地区マスタ」に登録した地区名（任意、例：さいたま市緑区）
      // pairId はご夫婦など同じ枠に2名を登録した場合、両者に同じ値を持たせて紐付けるためのID。
      // 実体としては2件の独立したbooking（別々のid）なので、編集・終了はそれぞれ個別に行える。
      // 対になっている予約は pairedBookingAt(booking) で取得できる。
      // hospitalized は④利用者検索・⑤入院管理表・①②のモーダル内チェックボックスのいずれからでも
      // ON/OFFできる（toggleHospitalized()）。booking自体は削除・移動せず、フラグを立てるだけ。
      // ON にすると①②の該当マスが黒色（.blk.hospitalized）になり、⑤入院管理表に一覧表示される。
      // 空き枠の集計・自動提案上は引き続き「使用中」の枠として扱われる（他の利用者には提案されない）。
    }
  },
  eventLog: [{type:'新規'|'終了', date, name, staff, day, slot, careManager, hospital, reason?}, ...],
  // reason（終了理由）は type:'終了' のときのみ。'入所'|'看取り'|'卒業' のいずれか
  // type:'終了' は、終了させる枠が「その利用者様（氏名一致）にとって最後の残り1枠」だった
  // ときだけ記録する（endBookingById()内で判定）。同姓同名で他の枠がまだ残っている場合は、
  // 利用者様自体の終了ではなく訪問頻度が減っただけとみなし、eventLogには記録しない
  // （＝⑦月次レポートの「終了」件数には加算されない）。
  referralSources: { careManagers: string[], hospitals: string[] },
  districts: string[] // 地区マスタ（⑨設定で追加・削除。③新規登録・提案の「地区」選択肢になる）
}
```

### 職種（role）とロールグループ
スタッフの`role`は`看護師`・`理学療法士`・`作業療法士`・`言語聴覚士`・`事務員`の5種類（`CAREGIVER_ROLES`が
前4つ、`THERAPIST_ROLES`が理学療法士・作業療法士・言語聴覚士の3つ）。理学療法士・作業療法士・言語聴覚士は
それぞれ独立した職種として区別する（法律上・臨床上スコープが異なるため、旧「セラピスト」という1つの
role では区別できなかったのを解消した）が、②空き状況の画面・時間帯（`slotLabels`）・空き枠数の計算調整
（`staffBuffer`）・⑨設定の勤務体系テーブルはこの3職種で引き続き1つの「セラピスト」として共有する。
この「特定のroleが実際にどのグループの画面・時間帯・staffBufferを使うか」を返すのが
`roleGroup(role)`（`THERAPIST_ROLES`に含まれていれば`'セラピスト'`、それ以外はそのまま）で、
`slotLabelsFor(role)`・`suggestionPool(role)`（buffer参照部分）・`removeSlot()`/`moveSlot()`など、
時間帯やstaffBufferに触れる箇所はすべてこの`roleGroup()`を経由する。一方`staffNames(role)`は
特定の職種（例：`'理学療法士'`）を渡せばその職種のスタッフだけを、グループ名`'セラピスト'`を渡せば
3職種combinedのスタッフ一覧を返す（②の空き状況テーブル・⑨の勤務体系テーブルはグループ名で呼び出して
3職種をまとめた1つの表にし、各行に`staffInfo(staff).role`で具体的な職種をタグ表示する）。
サービス時間の選択肢も職種で異なり、`durationOptionsFor(role)`が看護師は30/60/90分、
理学療法士・作業療法士・言語聴覚士は40/60分を返す（③新規登録・提案の各職種セクション、
④利用者検索・①②モーダルの編集フォームの両方で使用）。

**旧データ（役職「セラピスト」1本）からの移行**：この変更より前に登録されたスタッフは
`role:'セラピスト'`のまま保存されている。`staffNames(role)`は、グループ名`'セラピスト'`を
渡した場合（②空き状況・⑨設定の勤務体系表）だけでなく、理学療法士・作業療法士・言語聴覚士
いずれか具体的な職種を渡した場合（③新規登録・提案の職種チップ・候補選定・担当スタッフ指定欄）
でも`role==='セラピスト'`の旧データを後方互換として含める。そのため移行前でも②③⑨の
どこからも消えることはなく、③の「担当スタッフ」欄でも理学療法士・作業療法士・言語聴覚士
いずれのチップからも選択でき、選択肢には`名前（セラピスト・要職種変更）`と表示して未移行で
あることが分かるようにしている。ただし②空き状況のスタッフ名の横には`staffInfo(staff).role`
をそのまま表示するため、移行が済むまでは具体的な職種名ではなく「セラピスト」と表示され続ける
（これは仕様通りで、バグではない）。新規追加時の`#newStaffRole`にはもう「セラピスト」という
選択肢自体は無いので、移行は⑧スタッフ管理の各行にある職種プルダウン（`.role-change-select`、
`changeStaffRole(name, newRole)`で`staff.role`を書き換えるだけ。予約は氏名で紐付いているため、
同じ「セラピスト」グループ内＝理学療法士・作業療法士・言語聴覚士の間での変更であれば時間帯・
勤務体系データの互換性に問題は生じない）から行う。旧データはプルダウンに
「セラピスト（要選択）」という一時的な選択肢として表示され、管理者に正しい職種への変更を促す。
移行が完了すると、②のスタッフ名の横にも具体的な職種名が表示されるようになる。
- 1つの(staff, day, slotIdx)に対して複数の`booking`が共存できる（隔週・月次ローテーション対応、
  および同じ枠に2名を登録するご夫婦・ペア登録も同様の仕組みで実現している）。
  週の重複チェックは`isRotationFree()` / `isFullyFree()`を参照。
- 隔週・月次パターン（③新規登録・提案で「隔週」「月1回」を選んだ場合）の自動提案
  （`findRotationSuggestions()`）は、週が重ならなければ既存の隔週・月次利用者様と同じ枠に
  組み合わせることを最優先で探す（例：Aさんが第1・3週、Bさんが第2・4週なら、別のスタッフの
  新しい枠を開けるのではなく、同じ枠に2人ともまとめる）。具体的には、まず
  `occupiedWeeksAt(staff,day,slotIdx)`が空でない（＝すでに誰か隔週利用者様が入っている）
  かつ候補の週と重ならない枠を希望曜日・時間帯の優先順で探し（`matched:true`、提案タグは
  「第一候補（既存の隔週・月次予約と同じ枠に組み合わせ）」）、それで3件に満たない場合だけ、
  従来どおり完全に空いている枠を勤務予定人数が少ないスタッフから探す（`matched:false`）。
  組み合わせ候補は`.sugg-card`にtier2（インディゴ）のハイライトを付けて視覚的にも分かりやすくしている。
- `staff`配列の並び順がそのまま①②の表示順になる（⑧スタッフ管理の↑↓で自由に並べ替え可能）。名前も直接書き換え可能
  （`renameStaffMember()`が`staffWorkSlots`・`bookings`・`eventLog`内の旧名称もまとめて置き換える）。
- スタッフの資格・専門性（`qualifications`）は複数登録可能。「特定行為看護師」「ケアマネジャー」の
  プリセットに加え、「○○認定看護師」「○○専門看護師」「他ライセンス」は自由記述の接頭辞を付けて
  登録できる。画面表示（`roleLabel()`）は資格があればそちらを優先し、なければ`role`（具体的な職種名）
  を表示する。`事務員`は①②の対象外（⑧の職員名簿にのみ表示）。
- 時間帯（`slotLabels`）は「看護師」と「セラピスト（理学療法士・作業療法士・言語聴覚士で共有）」の
  2系統の配列。⑨設定でそれぞれ独立して追加・削除・並べ替え・名前変更ができる
  （`slotLabelsFor(role)` / `slotCount(role)`を参照。内部で`roleGroup(role)`を経由するため、
  具体的な職種を渡しても正しくグループの時間帯配列を返す）。
- スタッフの勤務体系（`staffWorkSlots`）は曜日単位ではなく「曜日×時間帯（枠）」単位で管理する。
  ⑨設定の勤務体系表は①の空き状況と同じ見た目のマス目（`.blk`ボタン）で、タップするとその
  スタッフ・その曜日・その枠だけをON/OFFできる（`worksOnSlot(staff,day,slotIdx)`で判定）。
  お昼で退勤する日、特定の枠だけ土日出勤するスタッフなど、曜日によって勤務する枠が異なる
  ケースに対応している。`worksOn(staff,day)`はその曜日にひとつでも勤務枠があるかの判定に使う
  （空き状況の土日欄を出すかどうかなどに利用）。
- ①②の「空き余地」の集計と自動提案の曜日探索は、土曜・日曜を定休日として自動的には対象にしない
  （`orderedDays()`参照）。土日欄はマス目ではなく、その日にその枠のどこかで実際に予約がある
  利用者名だけを箇条書きで表示する（クリックで通常どおり編集・終了操作が可能）。特定の利用者が
  土日を希望する場合は、⑨でそのスタッフの該当曜日・該当枠を個別にONにしたうえで通常どおり登録
  すればよい。訪問頻度パターンに「毎日（月〜日・週7回、土日訪問あり）」（`daily7`）を用意しており、
  これを選ぶと自動提案・自動登録も土日を含めて探索する（`includeWeekend`フラグで制御）。
  また③新規登録・提案には「特例」チェックボックス（`#f-weekend-exception`）があり、これをONにすると
  ⑨設定の勤務体系（ON/OFF）に関わらず土日を候補に含めて提案する（`weekendException`パラメータで
  `findWeeklySuggestions()` / `findRotationSuggestions()`に伝搬）。⑨設定自体は書き換えないその場限りの
  例外登録で、登録後は①②の該当曜日欄に通常どおり利用者名が箇条書きで表示される。土日に希望日を
  指定したい場合は希望曜日チップで「土」「日」を選択できる。
- ①②の「週2（2枠）／人」「週1（1枠）／人」は、曜日ごとの空き余地の合計（月〜金）から算出する
  独立した数字（曜日別カードとは別枠で表示）。
- 「空き枠数の計算調整」（⑨設定の看護師・セラピストごとの差引人数）は、①②の表示だけでなく
  ③新規登録・提案の候補選定にも反映される。実装は`suggestionPool(role)`で、勤務予定人数が
  最も少ない（＝一番余裕があるように見える）スタッフから順に差引人数分を候補から除外する方式。
- ③新規登録・提案の「職種」（`#roleChips`、`selectedRoles`）は看護師・理学療法士・作業療法士・
  言語聴覚士の4つから複数選択できる（旧・単一選択の`<select id="f-role">`から置き換え）。
  選択した職種の数だけ`#roleSections`内に職種専用のフォーム一式（`buildRoleSections()`が生成）が
  並び、各セクションが訪問頻度パターン・毎週の場合の回数・希望曜日・特例チェック・希望時間帯・
  サービス時間をそれぞれ独立して持つ（例：看護師は月1回・理学療法士は週2回、といった組み合わせが
  1回の登録操作で指定できる）。曜日・時間帯チップの選択状態は`selectedDaysByRole[role]` /
  `selectedSlotsByRole[role]`に、パターン変更時のUI切り替えは`updatePatternUIFor(role)`に、それぞれ
  職種名をキーとして保持する。サービス時間の選択肢は`durationOptionsFor(role)`により看護師のみ
  30/60/90分、理学療法士・作業療法士・言語聴覚士は40/60分となり、「同じ枠にもう1名を登録する」
  （ご夫婦・ペア登録、30分枠限定）の機能も看護師のセクションにのみ表示する。
  疾患名・主保険・独居・居宅介護支援事業所・医療機関・地区・実施時刻メモ・備考は職種に依存しない
  共通項目として`#roleSections`の外に1回だけ表示する。フォーム送信時は選択された職種それぞれについて、
  その職種自身のパターン・回数・曜日・時間帯を使って`findWeeklySuggestions()`/`findRotationSuggestions()`
  を個別に実行し、職種見出し付きで提案カードを並べて表示する（`data-role`属性でどの職種の提案か判別）。
  一方の職種の提案を確定（`confirmSuggestion(s, patient, patternValue, role)`）しても、氏名・疾患名等の
  共通入力とフォーム表示はそのまま保持され、もう一方の職種の提案カードも残るので、続けて確定できる
  （すべての職種を確定し終えたときだけフォームをリセットする）。同じ利用者様を複数職種で1回の
  登録操作にまとめられる。
- 各職種セクションには「担当スタッフ（未選択＝指定なし）」という`<select class="f-preferred-staff">`
  があり、デフォルトは先頭の「指定なし」（`value=""`）。指定なしのままなら従来通り
  `suggestionPool(role)`（空き枠数の計算調整を反映した候補プール）から自動で探すが、特定のスタッフを
  選ぶと`findWeeklySuggestions()`/`findRotationSuggestions()`の`pool`をそのスタッフ1名だけに絞り込む
  （空き枠数の計算調整による除外よりも、この明示的な指定を優先する）。該当スタッフに空きが無い場合は
  「「〈スタッフ名〉」さんの条件に合う空き枠が見つかりませんでした」という専用の案内を表示する。
  ④利用者検索の患者カードの「＋ 訪問を追加する」（`goToIntakeToAddVisit()`）から遷移した場合のみ、
  既存予約と同じ担当スタッフをこの欄にあらかじめ選択しておく（`prefillFromExistingBooking(b, silent,
  includeStaff)`の第3引数）。一方、③新規登録・提案内の「登録済みの内容を引き継ぐ」ボタン（同じ
  `prefillFromExistingBooking()`を`includeStaff`なしで呼ぶ）では担当スタッフは引き継がない
  ——ここで引き継いでしまうと、氏名だけ書き換えて別の利用者様を登録するときに、無関係な提案が
  1名分だけに絞られてしまい候補が出ない・気づきにくい形で偏るため、あえて分けている。
- 訪問頻度パターンの`<select>`は「毎週」「隔週」「月1回」の`<optgroup>`で整理し、各`<option>`の

  変更していないため、既存の予約データの互換性には影響しない。

  ④利用者検索から該当の枠だけを個別に終了すればよい。

  空いているかを`isRotationFree(newStaff,newDay,newSlotIdx,orig.weeks)`でチェックしたうえで予約

  同じ枠に表示される2枚のカードをそれぞれ個別に編集・終了できる。
- 各画面の「🖨 PDF出力」ボタンはブラウザの印刷機能（`window.print()`）を呼び出す実装。専用ライブラリは

  疾患名・主保険・独居・地区の内訳表も表示する（⑥リスト分析の紹介元分析と同じ集計ロジックを再利用）。

- ①②の空き状況ヘッダー右側には「🔔 受け入れ枠アラート」を表示する。月〜金・曜日×時間帯（枠）ごとに、
  空き枠数の調整（バッファ）を差し引いたうえで空いているスタッフ数を数え、2件以上空いている
  枠を一覧表示する（`computeSlotAlerts(role, threshold)`）。しきい値は関数の引数で変更できる。

  従来どおり全幅で表示される（勤務表と横並びにすると土日欄が圧迫されるため分離している）。

  できてしまわないよう、`renderOverview()`の末尾で`syncOverviewAlertHeight(role)`を呼び、
  サマリーカード列の実測高さ（`#ovMain-<role>`）をアラート枠（`#ovAlert-<role>`）にJSで
  反映して揃えている（アラート内の一覧はその高さの中で内部スクロールする）。スタッフ0名時の
  早期returnでも揃えるようにしているほか、`ResizeObserver`で`#ovMain-<role>`を監視し続け、
  表示後にサマリーカード列の高さが変わった場合でも自動的に揃え直す。
  なお空き状況の「土曜・日曜は定休日のため…」という注記文は、ユーザー要望により削除済み。
  サマリーカード列（`.ov-main`）には`max-width:620px`を指定している。これが無いと、
  「空き枠数の計算調整」の注記文（バッファが0より大きいスタッフ職種でのみ表示される長い1文）
  がラップされずに`flex:0 0 auto`のshrink-to-fit幅を押し広げてしまい、看護師側だけアラート枠
  （`flex:1`で残り幅を埋める）が極端に狭くなって1列表示になる、という左右非対称な不具合が
  起きていた。max-widthで固定してテキストを折り返させることで、注記文の有無に関わらず
  アラート枠の横幅が常に揃うようにしている。あわせて注記文自体も「※〈職種〉 N名分を
  勤務予定人数から差し引いて計算しています」まで短縮し（補足の「⑨設定で変更できます…」
  部分は削除）、視認性を上げている。
- ④利用者検索（旧・終了処理）は、単に予約を終了するだけの画面ではなく、氏名検索でヒットした
  利用中の予約について「編集する」（①②のスロットモーダルを`openSlotModal(staff,day,slotIdx)`
  で直接開き、曜日・時間帯や各種情報を変更できる）・「終了する」・「＋ 訪問を追加する」（後述）
  をその場で行えるようにしたもの。
- 患者カードの「＋ 訪問を追加する」（氏名が入力されている場合のみ表示、`goToIntakeToAddVisit(name)`）
  を押すと、③新規登録・提案に切り替わり、氏名・疾患名・主保険・独居・居宅介護支援事業所・医療機関・
  地区といった共通項目と、既存予約と同じサービス時間（`prefillFromExistingBooking()`）、既存予約と
  同じ職種のチップをあらかじめ引き継いだ状態で開く（複数職種の予約がある利用者様なら、その全職種の
  チップがまとめて選択される）。氏名を引き継いだ時点で③の「既に◯件ご利用中です」の案内も自動的に
  表示される。管理者は希望曜日・時間帯・訪問頻度パターンだけを選んで「空き枠を探す」を押せば、
  同じ利用者様の追加の訪問枠をその場で登録できる（氏名を手入力し直したり、「登録済みの内容を
  引き継ぐ」を別途クリックしたりする必要がない）。パネル切り替えの共通処理は`switchPanel(name)`
  に切り出し、ナビのクリックとこのショートカットの両方から呼び出している。
- 患者カードの「📄 週間予定表を発行」（氏名が入力されている場合のみ表示、`printPatientSchedule(name)`）
  は、利用者様・ご家族にお渡しする「週間訪問予定表」を1枚のPDFとして発行する機能。専用のPDFライブラリは
  使わず、既存の🖨PDF出力（`window.print()`）と同じ考え方で、`window.open('', '_blank', ...)`で
  空のポップアップウィンドウを開き、そこに`buildPatientScheduleHtml(name, bookings)`が組み立てた
  完全な1ページ分のHTML（インラインCSS込み）を`document.write()`で書き込み、`window.print()`を
  呼び出す（ブラウザの印刷ダイアログから「PDFとして保存」を選べば実質PDF化できる）。
  `document.write()`/`document.close()`の時点で`load`イベントが同期的に発火してしまうことがあり、
  その後で`addEventListener('load', ...)`を仕込むと間に合わず印刷が呼ばれないことがあったため、
  `document.close()`の直後に`win.print()`を直接呼ぶ実装にしている。
  - デザインはユーザーが提示した手書き用「週間スケジュール表」テンプレート画像を参考にしている。
    見た目は横一列の7カラム表ではなく、**曜日ごとに1行**（`曜日`・`日付`・`内容`の3列）を縦に積む
    表形式（`SCHEDULE_DAY_ORDER = ['月','火','水','木','金','土','日']`、月曜始まり。アプリ内部の
    `DAYS`と同じ並び）。`日付`列は`scheduleWeekDates()`が「発行した日を含む週」の月曜を起点に
    各曜日の月/日を計算して埋める（テンプレート画像では空欄だった「/」の部分に実際の日付が入る）。
  - 学会名・ロゴ・担当スタッフ氏名は表示しない（利用者様にお渡しする書類のため、団体名や個人の担当者名を
    載せない仕様にしている）。`内容`列には時刻と職種（看護師／理学療法士／作業療法士／言語聴覚士、
    `roleLabel()`）だけをプレーンなテキストで表示し、色付きカードのような装飾はつけない。
  - 用紙はA4縦向き（`@page{ size:A4 portrait; }`）。文字はあくまで横書き（`writing-mode:horizontal-tb`
    を明示）で、曜日ごとの行を上から下に読んでいく構成にしている。
  - 土曜の行は薄い青、日曜の行は薄いオレンジで背景色を付け、テンプレート画像の配色に合わせている
    （文字色はどの曜日も黒のまま）。1日に複数回訪問がある場合は`内容`列の中に時刻・職種を1行ずつ
    点線区切りで並べ、隔週・月次パターン（例：「隔週（第1・3週）」）の予約はその行に括弧書きで
    パターン名を併記する。予約が無い曜日は空欄のまま（テンプレート画像と同様、記号は入れない）。
  - 現在ご利用中の予約が1件も無い利用者様に対して押した場合は、発行せずアラートで案内する。
- 週複数回訪問（例：毎日パターンで月〜金の5枠）の利用者は、同じ氏名（前後の空白を除いて完全一致）の
  予約が複数件生成されるが、これらを一覧上でバラバラの行として並べると同一人物の情報が重複表示
  されてしまうため、`groupBookingsByPatient(rows)`で氏名ごとに予約をグルーピングし、
  `buildPatientCard(bookings)`で1人につき1枚の「患者カード」（`.patient-card`）にまとめて表示する。
  氏名未入力の予約は`__anon_<id>`という予約IDベースの一意キーを使い、誤って1つに統合されないように
  している。カードの見出しには氏名と（複数枠の場合のみ）「（週N回・N枠）」という頻度メモを表示し、
  疾患・独居・居宅介護支援事業所・医療機関・地区といった共通の属性情報はカード内に1回だけ表示する
  （同じ利用者様を看護師・セラピスト両方で登録した場合も、この氏名グルーピングにより1枚のカードに
  両方の枠がまとまる）。カード内部の各予約枠は`.patient-slots`内の`.end-row`として、曜日・時間帯・
  担当者・パターン・（ペア枠がある場合は）同枠のペア相手といった枠ごとの情報と「編集する」ボタンを
  表示する（行ごとの「終了理由を選択」「終了する」は廃止し、下記の通りカード上部にまとめた）。
  予約が2件以上あるカードでは、各行に「削除」ボタンも並べて表示する（1件だけのカードでは、
  その1件を削除する＝利用者様自体の終了になるため、下記のカード上部の「終了理由を選択」＋
  「終了する」に一本化しており、行の「削除」は表示しない）。
- 「入院中」チェックは、カード全体に1つだけ表示される「入院中（すべての枠に適用）」チェックボックス
  （`.hospitalized-check-group`）を操作すると、そのカードに含まれる全予約IDに対して一括で
  `toggleHospitalizedGroup(ids, checked)`が呼ばれ、`booking.hospitalized`をまとめて切り替える
  （個別の予約1件だけを入院中にしたい場合は、①②のスロットモーダル内の個別チェックボックスから
  `toggleHospitalized(id, checked)`を使う）。予約自体は削除・移動しない（一時的に入院しても、
  退院後は同じ枠がそのまま復帰する）。ON にすると①②の該当マスが黒色（`.blk.hospitalized`、凡例に
  追加済み）で表示され、土日欄（一覧表示）でも氏名の後ろに「（入院中）」と表示される。空き枠の
  集計・自動提案では引き続き「使用中」の枠として扱われる（入院中でも他の利用者には提案されない）。
  トグル自体は④利用者検索の一覧・⑤入院管理表の一覧・①②のスロットモーダル内チェックボックスの
  どこからでも操作でき、どこで変更しても他の画面に即座に反映される。
- 予約の一部だけを削除して頻度を減らす（例：週5回→週4回）操作と、利用者様のサービスをすべて
  終了する操作を、はっきり別のボタンに分けている。
  - **行の「削除」**（`deleteBookingById(id)`、予約が2件以上あるカードのみ表示）：その1枠だけを
    確認ダイアログのうえ即座に削除する。理由の入力は求めず、`eventLog`にも何も記録しない
    （＝⑦月次レポートの「終了」件数には一切影響しない）。利用者様自体は継続中で、単に訪問頻度が
    減っただけのケースに使う。
  - **カード上部の「終了理由を選択」＋「終了する」**（`endAllBookingsForPatient(ids, reason)`）：
    カードに含まれる予約IDすべて（`ids`、1件でも複数件でも）を対象に、理由を選んだうえでまとめて
    終了する＝利用者様のサービスが全て終了したものとして扱う。件数に関わらず`eventLog`には
    「終了」イベントを必ず1件だけ記録するため、週5回訪問していた利用者様が終了しても⑦月次レポート
    の終了数は1件として集計される（枠の数だけ加算されることはない）。予約が2件以上あるカードでは
    「すべての訪問（N件）を終了します」という注記を、確認ダイアログにも件数を表示する。
  - なお①②のスロットモーダル内の「終了する」（`bookingReadView()`の`data-end`ボタン）は、この
    カード単位の再設計より前からある個別の入口で、`endBookingById(id, reason)`が引き続き対応する
    （他に同姓同名の予約が残っているかを自動判定し、残っていればeventLogへの記録を省略する、
    という従来通りの1件単位のロジック）。
- ⑤入院管理表（`renderInpatientList()`）は、`booking.hospitalized===true`の予約だけを対象に、
  同じ`groupBookingsByPatient()`／`buildPatientCard()`を使って④利用者検索と同じ患者カード形式で
  一覧表示する専用画面（1人が複数枠すべて入院中なら1枚のカードに全枠がまとまり、一部の枠だけ
  入院中の場合はその枠だけがカードに含まれる）。入院中の利用者をまとめて把握し、退院時にチェックを
  外す・そのまま終了する、といった運用を想定している。

## 既知の制約・今後の検討事項
1. **同時編集は後勝ち（last-write-wins）**：複数管理者がほぼ同時に保存すると、後から保存した方の
   内容で上書きされる（競合検知や警告表示はまだ実装していない）。編集がぶつかることが実際に
   問題になるようなら、楽観ロック（保存時のタイムスタンプ比較）の追加を検討。
2. **入力値のエスケープ**：利用者名・疾患名などは画面表示時にHTMLエスケープしていない
   （信頼できる内部スタッフのみが入力する想定のため、現状は許容している）。外部にも公開する場合は要対応。
3. **Excelとの連携なし**：元のExcel（訪問予定表_最新版.xlsx）とこのアプリは同期していない。
   どちらかをメインの記録にするか、連携の仕組みを作るか要検討。
4. **紹介元分析の「割合」の定義**：現状は「自社の現在の利用者全体に占める、その紹介元のシェア」
   として計算している（各事業所側の全利用者数に対する割合ではない）。要件次第で変更が必要。
5. **利用者の同一性判定が名前ベース**：同姓同名がいると紹介元分析などで名寄せが誤る可能性がある。
   本格運用する場合はID採番を検討。
6. **管理者ログインは共通パスワード1つ**：誰がいつ編集したかは記録されない。個人ごとの操作履歴が
   必要になった場合は、アカウントを分ける仕組みへの変更を検討。
